● I wrote the overview to docs/kernel_overview.md, decided all the open
  questions, and wrote no code. Nothing is committed yet.

  What you asked:
  - Does ls run in parallel with the shell? No. The shell calls
    exec("/bin/ls.bin") and waits inside that call, like DOS. The kernel loads
    ls into memory just above the shell and calls it like a function. When ls
    returns, exec returns and the shell prints the next prompt.
  - What executes what: the shell reads a line and asks the kernel to run ls. ls
    asks the kernel for directory entries, formats its lines, and calls write.
    Every one of those requests goes through a table of kernel addresses.
  - What gets the output "into the shell": the kernel's console. It owns the
    cursor and the 32×12 text grid, and both the shell and ls just call write on
    it, one after the other. The shell never receives ls's output. Its prompt
    simply lands below ls's lines.

  Decisions: I recorded each one inline where the question was asked, in
  kernel.md, kernel_exec.md and kernel_changes.md. §6 of the overview has the
  full table. The main ones:
  - Programs use system calls for the disk and the console, and are relocated
    into memory above whoever started them.
  - CPU work now: reading and setting the stack pointer, faults, interrupts, the
    timer and Ctrl-C. Multitasking comes later.
  - The shell restarts when it exits, and the kernel's console handles line
    editing.
  - printf comes from adding variadic functions to the compiler, capped at 8
    extra arguments.
  - ls > file redirection comes later.

  One design fix: the kernel docs put the system-call table at 0x15818, but
  bios2 now leaves the boot sector copy and boot channel there. I moved the
  table to 0x15A1C and updated the docs to match.

  The overview ends with the build order. Relocatable programs come first.

❯ so what exactly is the shell doing? is it just a text input/graphics?         

● Neither. The shell draws nothing and doesn't read keys itself; the kernel's
  console does both. The shell only decides what the line you typed means and
  asks the kernel to run it. On a Unix machine the terminal is what shows text
  and takes keys, and the shell is the program that interprets the commands.

  Who does what:

  ┌─────────────┬───────────────────────────────────────────────────────────┐
  │    Part     │                            Job                            │
  ├─────────────┼───────────────────────────────────────────────────────────┤
  │ Keyboard    │ Queues the keys you press                                 │
  │ device      │                                                           │
  ├─────────────┼───────────────────────────────────────────────────────────┤
  │ Kernel's    │ Turns keys into a line (echo, backspace, Enter) and draws │
  │ console     │  all text on the screen, with the cursor and scrolling    │
  ├─────────────┼───────────────────────────────────────────────────────────┤
  │ Shell       │ Reads a line, works out what it means, runs it, and       │
  │             │ repeats                                                   │
  ├─────────────┼───────────────────────────────────────────────────────────┤
  │ Kernel's    │ Loads and runs the program the shell names                │
  │ exec        │                                                           │
  └─────────────┴───────────────────────────────────────────────────────────┘

  The shell's whole job is one loop:

  for (;;) {
      write(1, "> ", 2);                  // prompt: the console draws it
      read(0, line, 255);                 // the console handles typing; the 
  shell gets "ls /docs"
      argc = split(line, argv);           // {"ls", "/docs"}, double quotes 
  group words
      if (argc == 0) continue;
      if (builtin(argc, argv)) continue;  // cd, exit, help: handled here, 
  nothing started
      path = find(argv[0]);               // /bin/ls.bin, then ls.bin in the 
  current directory
      if (!path) { print "ls: not found"; continue; }
      status = exec(path, argc, argv);    // ls runs; the shell waits here
      if (status != 0) print the error    // e.g. "exited with 1" or "crashed"
  }

  What it does itself:
  - Splits the line into words.
  - Runs its built-in commands. cd has to be one, because the current directory
    has to change in the kernel, not in a program that then exits.
  - Finds the program file from the name you typed.
  - Reports problems, such as "not found", a non-zero exit, or a crash.
  - Later, redirection: it would spot > file and tell the kernel where the
    output goes.

  What it doesn't do: draw text, handle keys, load programs, or touch the disk
  directly. Those all belong to the kernel.

  So it's a small program, probably a couple of hundred lines of C, and you
  could swap in a different shell without changing the kernel.

❯ okay before doing anything. i want to know that how can the kernel and shell  
  run at the same time if we dont support multitasking? please explain hjust    
  here in the chat.                                                             

● They don't run at the same time. Only one of them is ever executing; they take
  turns through ordinary function calls. "Running" here means "somewhere on the
  call stack", not "executing right now".

  The kernel isn't a process that keeps running. It's code sitting in memory
  that runs only when something calls it:

  1. At boot the kernel runs, sets things up, and then calls the shell's entry
     point, like calling a function. The kernel is now paused inside that call.
  2. The shell runs. When it needs something, such as a typed line, it calls a
     kernel function through the system-call table. The shell pauses and the
     kernel code runs.
  3. The kernel function finishes and returns, and the shell continues.

  At any moment the CPU executes exactly one instruction. The stack just
  remembers who called whom:

  kernel_main          paused, waiting for the shell to return
   └ shell main        paused, waiting for read() to return
      └ kernel read()  ← the CPU is HERE: waiting for Enter

  After Enter, read returns and the CPU is in the shell again. When the shell
  runs ls, ls goes on top of that stack in the same way.

  It works like a library. When your C program calls strlen, the program and
  strlen aren't running in parallel: the program pauses and strlen runs. The
  kernel is the same idea, except its functions own the disk, the screen and the
  keyboard, and it happened to be the first code to run.

  What multitasking would add is two programs that are both in the middle of
  their work without one having called the other. For example, the shell keeps a
  clock ticking while ls runs. That needs a timer interrupt to forcibly pause
  one program and switch to the other, which is the optional later step.

  Interrupts in the first version don't change this. Once the CPU changes are
  in, the timer or Ctrl-C can briefly jump into the kernel and back, but that's
  still one thing at a time: a very short interruption, not parallel running.
